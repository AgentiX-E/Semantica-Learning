Graph-Native Infrastructure

Semantica：为 AI 系统搭建的「上下文与问责」基础设施

大多数 AI Agent 做事不留痕迹——它们存的是 embedding（向量），而不是 meaning（意义）。Semantica 坐在你的 LLM、向量库、Agent 框架之下，作为一个确定性基础设施层，让每一次决策都可追溯、可审计、可解释。

◈

一句话理解：Semantica 是「AI Agent 的开源 Palantir」。它把企业的数据摄取进来，抽取关键信息，构建 Context Graph 与知识图谱（KG），再在其上运行图分析与因果推理，并内建完整的决策溯源（provenance）——默认可解释、可追踪、可信任。

它到底解决什么问题？

以一个受监管场景为例：贷款审批。一个风控 Agent 批准了一笔贷款，数月后监管机构问「为什么？」。如果答案是「向量相似度 0.87」，这是合规灾难；如果答案是「这个决策由哪些事实支撑、沿用了哪条历史判例、施加了哪条策略规则、谁在何时依据什么做出的」，这才是监管认可的格式。

🕸

Context Graph

把 Agent 知道的、决策的、推理的一切，组织成一张可查询的结构化图，而非一堆扁平的 embedding。

🎯

决策智能

每个决策都是一等公民：可追溯、可按判例检索、可因果关联。不再是转瞬即逝的日志。

⚖

审计与治理

每个事实都带 W3C PROV-O 溯源；SHACL 约束、冲突检测、OWL 生成，输出监管可直接采信的审计轨迹。

Semantica vs 其它方案

它不替代你的 LLM、向量库或 Agent 框架，而是在其之上叠加决策记录、因果推理、溯源、本体治理、冲突检测与审计轨迹。核心推理引擎、KG 构建与溯源层完全确定性——无需 LLM 即可使用。

⚠

系统级可解释性，而非基础模型可解释性。Semantica 不解释 LLM 内部发生了什么（思维链依然不透明）。它解释的是模型外部的一切：喂进去的上下文与数据、产生的决策、其溯源、相关关系、施加的策略、完整的执行轨迹。

为谁而建？

AI/ML 平台团队

让 Agent 做出高影响决策，需要的是可查询的结构化上下文，而不是一个向量索引。

数据平台团队

把 Databricks / Snowflake 里已有的表，就地转成治理化、血缘可追踪的知识图谱，无需先导出到第三方 SaaS。

合规 / 风险 / 审计团队

对「AI 为什么这么做？」给出监管真正能接受的答案。

受监管企业

金融、医疗、法律、政府、国防——不能上黑盒，也不能把数据交给别人的 SaaS。

一个 5 秒的直觉示例

Python · 决策智能
from semantica.context import ContextGraph

graph = ContextGraph(advanced_analytics=True)

decision_id = graph.record_decision(
    category="vendor_selection",
    scenario="Choose cloud provider for HIPAA workload",
    reasoning="AWS offers BAA, mature HIPAA tooling, and existing team expertise",
    outcome="selected_aws",
    confidence=0.93,
)

chain     = graph.trace_decision_chain(decision_id)          # 完整因果祖先
similar   = graph.find_similar_decisions("cloud vendor", max_results=5)  # 历史判例
impact    = graph.analyze_decision_impact(decision_id)       # 下游影响图
compliant = graph.check_decision_rules({"category": "vendor_selection"})  # 策略门禁

Core Concepts

核心概念：知识图谱、GraphRAG、推理与溯源

Semantica 把非结构化数据（文档、网页、报告、数据库）转化为知识图谱——AI 系统可以查询、推理、回溯到来源的结构化表示。核心就三层：上下文层、问责层、扩展层。

上下文层

知识图谱、GraphRAG 检索、语义 embedding、时序智能，把每个 LLM 响应锚定在结构化、可查询的事实上。

问责层

溯源追踪、决策智能、冲突检测、W3C PROV-O 合规，让每个断言可审计、可解释。

扩展层

PluginRegistry 与 MethodRegistry 让你替换/增强任何组件，无需改动框架代码。

知识图谱（Knowledge Graph）

知识图谱用三种积木存储信息：节点（实体）、边（关系）、属性。这种结构让知识变得可搜索、可连接、可查询、可解释——每个答案都能回溯到产生它的事实与关系。

三元组示例
(Apple_Inc, founded_by, Steve_Jobs)
(Steve_Jobs, works_for,  Apple_Inc)   ← 与上一句冲突！
(Apple_Inc, located_in, Cupertino)

实体抽取（NER）与关系抽取

输入一句「Apple Inc. was founded by Steve Jobs in 1976 in Cupertino.」，抽取器输出带类型的实体与它们之间的有向关系：

从一句话到知识图谱：端到端走一遍

把上面的过程串起来，你就能直观理解 Semantica 的「消化系统」是怎么工作的：

  1. 输入文本——"Apple Inc. was founded by Steve Jobs in 1976 in Cupertino."
  2. NER 抽取实体——识别出 Apple Inc.（ORG）、Steve Jobs（PERSON）、1976（DATE）、Cupertino（LOCATION）。
  3. 关系抽取——识别 (Steve Jobs, founded, Apple Inc.) 与 (Apple Inc., located_in, Cupertino)。
  4. 构图——GraphBuilder 把实体变成节点、关系变成有向边。
  5. 溯源——每个节点/边记录「来自哪份文档、用哪种抽取方法」。

这一步的产出，就是后面所有推理、决策、审计的基础。记住这条链：文本 → 实体 + 关系 → 三元组 → 图 → 溯源。

知识图谱 vs 向量库

两者都为 AI 检索存储信息，但用途不同：

存结构化事实（带类型节点 + 有标签边），回答需要理解实体间关系的问题。

遍历多跳查询：「苹果校友后来创办了哪些公司？」
可解释性每个答案回溯到具体节点与边，非黑盒
时序推理时点查询、valid_from/valid_until 窗口、历史快照
冲突检测两个源对同一事实的分歧被浮出并解决

存文本块的稠密向量，靠语义相似度找相关内容，适合「答案结构未知」的场景。

模糊相似即使措辞不同也能找到相关内容
速度大规模亚毫秒近似最近邻
非结构化文本直接作用于段落、句子、原始文档
简单无需 schema 设计，嵌入即索引

Semantica 把两者结合：向量检索先锚定起点节点，图遍历再提供向量库给不了的结构与溯源。

查询嵌入查询被嵌入，用向量相似度找锚点节点
图遍历从锚点节点多跳遍历，取回相关实体与关系
上下文组装事实 + 关系，每个断言都带来源归因
LLM 生成LLM 基于结构化上下文生成答案，消除幻觉

六种推理引擎

Semantica 内置多种推理引擎，从已有事实派生新知识：已知「Steve Jobs 创办了 Apple」与「Apple 总部在 Cupertino」，可推出「Steve Jobs 与 Cupertino 有关联」。

引擎原理最佳场景
前向链反复应用 IF/THEN 规则直至不动点告警系统、合规检查
Rete 网络高效模式匹配，避免重算未变前提海量规则 + 高吞吐事实
演绎经典三段论，前提→必然结论数学与逻辑推理
溯因为证据推断最可能解释诊断、调查
SPARQL基于查询的 RDF 推理语义网、本体推理
Datalog递归 Horn 子句 + 不动点传递闭包、图可达性

Embedding 是怎么工作的？

Embedding 把文本变成稠密数值向量，让 AI 能度量语义相似度——即使措辞不同，含义相近的文本在向量空间里也靠得近。

◉

直觉：把「Apple」「苹果公司」「水果」想象成三维空间里的点。Apple 与 苹果公司 距离很近（语义相同），与 水果 距离稍远（有歧义）。余弦相似度度量两个向量的夹角——同向为 1，正交为 0。

Semantica 用 embedding 做五件事：语义检索（按意义而非关键词）、实体消歧（跨源匹配同一实体）、判例检索（找相似历史决策）、GraphRAG 检索（混合向量 + 图遍历）、距离智能（任意节点集间的 N×N 语义距离矩阵）。

时序智能（Temporal）

知识会随时间变化。时序图为节点与边附加 valid_from / valid_until 窗口，支持时点查询与历史分析。支持 Allen 区间代数（全部 13 种时序关系）、OWL-Time 导出、recorded_at 戳记。

溯源与审计（Provenance）

Semantica 中每个事实都链接回：来源文档、抽取方法（pattern / ML / LLM）、构图时施加的本体规则、产生任何推理事实的推理步骤。这是 W3C PROV-O 合规的血缘，适用于 HIPAA、SOX、GDPR、FDA 21 CFR Part 11 等受监管行业。

插件与扩展机制

Semantica 为扩展而生。任何组件——摄取器、抽取器、图构建器、推理引擎——都能在运行时用自定义实现替换或增强：

PluginRegistry：按名称替换任意组件 ▸
Python
from semantica.core import PluginRegistry

registry = PluginRegistry()
registry.register_plugin(
    "my_sql_ingestor", MySQLIngestor,
    version="1.0.0",
    description="PostgreSQL ingestor for internal warehouse",
    capabilities=["ingest"],
)
plugin = registry.load_plugin("my_sql_ingestor", connection_string="postgresql://...")
MethodRegistry：按名注册领域图操作 ▸
Python
from semantica.kg import MethodRegistry
registry = MethodRegistry()
registry.register("supply_chain_hops", find_supply_chain_hops)
result = registry.call("supply_chain_hops", kg, source_node="Supplier_A", max_hops=5)

Data Pipeline

数据流水线：从任意源到最终制品

这是 Semantica 的「消化系统」——把多源异构数据一步步变成干净、可查询、可溯源的知识图谱。

Ingest：多源摄取

统一接口把数据加载为 SourceDocument 格式。支持本地文件、网页、数据库、Parquet、XML、Databricks、Snowflake、Git、邮件、消息流（Kafka/Kinesis/Pulsar）、MCP 资源等。

Python
from semantica.ingest import FileIngestor, WebIngestor, ParquetIngestor

docs    = FileIngestor().ingest_directory("./contracts/", recursive=True)
page    = WebIngestor(max_depth=2).ingest("https://example.com")
records = ParquetIngestor().ingest("data/events.parquet")

Parse：文档解析

从原始文档提取结构化文本与布局元数据。DoclingParser 额外处理多栏 PDF、合并单元格表格与 OCR。

Normalize：归一化

把数据标准化为一致的规范形式：日期转 ISO、实体名规范化、修复编码问题、剥离噪声，确保下游抽取在干净一致文本上工作。

Split：分块

为 embedding 与 RAG 流水线切分文本，同时保留语义边界。策略：recursive（递归）、semantic_transformer（语义边界）、entity_aware（实体感知）、relation_aware（关系感知）、sliding_window（滑窗）、structural（结构化）。

Extract：抽取（NER + 关系 + 事件 + 三元组）

Python
from semantica.semantic_extract import NERExtractor, RelationExtractor, TripletExtractor

ner      = NERExtractor(method="llm", llm_provider=llm)
entities = ner.extract("Apple Inc. was founded by Steve Jobs.")

rel           = RelationExtractor(method="llm", llm_provider=llm)
relationships = rel.extract(text, entities=entities)

trip = TripletExtractor(method="llm", llm_provider=llm)
triplets = trip.extract(text)

Knowledge Graph

知识图谱构建：GraphBuilder、实体消歧与时序模型

这是 Semantica 的「骨架」——把抽取出的实体与关系组装成可查询的图，并支持双时态事实与全图分析。

GraphBuilder

Python
from semantica.kg import GraphBuilder, PathFinder

builder = GraphBuilder(merge_entities=True)   # 自动消歧重复实体
graph   = builder.build({"entities": entities, "relationships": relationships})

finder = PathFinder()
path   = finder.dijkstra_shortest_path(graph, "Steve Jobs", "Tim Cook")

merge_entities=True 会自动把「Apple」「Apple Inc.」「AAPL」这类同一实体的不同写法合并，无需手动去重。

双时态事实（BiTemporalFact）

一个事实有两个独立时间维度：有效时间（valid time，它在真实世界何时为真）与事务时间（transaction time，它何时被系统记录）。这为缓慢变化的数据提供了完整审计轨迹。

Python · 时点查询
from semantica.kg import TemporalGraphQuery

tq = TemporalGraphQuery(enable_temporal_reasoning=True)
snapshot = tq.query_at_time(kg, query="", at_time="2021-06-15")

图算法（Graph Analytics）

中心性

PageRank、介数（桥接节点）、接近中心性——衡量节点重要性。

社区检测

识别内部连接密集的簇：主题社区、欺诈团伙、组织簇。

链路预测

预测实体间可能的关系，用于推荐与补全。

路径查找

Dijkstra 最短路、多跳路径查询。

距离智能

N×N 语义距离矩阵、ego-mode 邻域可视化、near/mid/far 距离带。

相似度

内容与结构相似度计算。

Reasoning

推理引擎：确定性的、可解释的推理

Semantica 的推理不是黑盒。每个推导出的新事实都携带产生它的规则与前提，形成可解释的推理路径。

反复应用 IF/THEN 规则直到没有新事实产生。适合告警系统、合规检查、触发器工作流。

Python
from semantica.reasoning import Reasoner, Rule, Fact, RuleType

engine = Reasoner()
engine.add_fact(Fact(subject="Alice", predicate="is_a", obj="Manager"))
engine.add_rule(Rule(
    rule_type=RuleType.FORWARD_CHAIN,

看一次推理是怎么「一步步」发生的

这是 Semantica 推理「可解释」的关键——每个新事实都记录了用了哪条规则、基于哪些前提。以前向链为例：

推理执行轨迹（trace）
已知事实:
  F1: Alice is_a Manager
规则:
  R1: IF (?x is_a Manager) THEN (?x has_authority true)

第 1 轮匹配:
  R1 的条件 [?x=Alice, Manager=Manager] ✓ 匹配 F1
  → 推导出新事实 F2: Alice has_authority true
  → 记录推理路径: F2 ← R1 ← [F1]

第 2 轮匹配:
  无新事实可推导 → 达到不动点，停止

最终结论 + 完整解释路径（可审计）:
  "Alice has_authority true"  ←  规则 R1  ←  前提 "Alice is_a Manager"
✓

为什么这很重要？黑盒推理只给你结论；Semantica 给你结论 + 规则 + 前提的完整链条。审计员能逐条验证，这就是「可解释 AI」在系统层面的落地。

TypeScript · 核心方法
export class ContextGraph {
  readonly nodes = new Map<string, GraphNode>();
  readonly edges: GraphEdge[] = [];
  private readonly adjacency = new Map<string, GraphEdge[]>();
  private readonly nodeTypeIndex = new Map<string, Set<string>>();

  addNode(id: string, type: string, content?: string, props = {}): boolean { /* ... */ }
  addEdge(source: string, target: string, type = "related_to", weight = 1.0): boolean { /* ... */ }

  // BFS 遍历：返回带 hop 距离的邻居
  getNeighbors(nodeId: string, hops = 1, relTypes?: string[], minWeight = 0.0): NeighborEntry[] {
    const visited = new Set([nodeId]);
    const queue = [[nodeId, 0, 1.0]];
    const neighbors: NeighborEntry[] = [];
    while (queue.length) {
      const [cur, hop, decay] = queue.shift()!;
      if (hop >= hops) continue;
      for (const edge of this.adjacency.get(cur) ?? []) {
        if (relTypes && !relTypes.includes(edge.type)) continue;
        if (edge.weight < minWeight) continue;
        const nb = edge.target_id;
        if (visited.has(nb)) continue;
        visited.add(nb);
        queue.push([nb, hop + 1, decay * edge.weight]);
        neighbors.push({ id: nb, relationship: edge.type, hop: hop + 1 });
      }
    }
    return neighbors;
  }

  // 时序快照：返回某时点活跃的节点与边
  stateAt(at: string | Date): GraphData {
    const d = at instanceof Date ? at : new Date(at);
    return {
      nodes: [...this.nodes.values()].filter(n => isActive(n.validFrom, n.validUntil, d)),
      edges: this.edges.filter(e => isActive(e.validFrom, e.validUntil, d)),
    };
  }
}
✓

关键洞察：BFS 遍历里用 decay * edge.weight 累积「置信度衰减」，这样多跳之后你能知道一条关系链的可信度还剩多少——这正是 Semantica 的 include_distance_metadata 在做的事。

前向链推理的核心：合一（unification）

TypeScript · 合一算法
function unify(pattern: TriplePattern, fact: Triple): Map<string, string> | null {
  const bindings = new Map<string, string>();
  const pairs = [
    [pattern.subject, fact.subject],
    [pattern.predicate, fact.predicate],
    [pattern.object, fact.object],
  ];
  for (const [p, f] of pairs) {
    if (p.startsWith("?")) {           // 变量
      const existing = bindings.get(p);
      if (existing !== undefined && existing !== f) return null;
      bindings.set(p, f);
    } else if (p !== f) {              // 常量必须相等
      return null;
    }
  }
  return bindings;
}

Datalog 递归（传递闭包）

Datalog 用自底向上半朴素不动点求值，处理前向链无法表达的递归关系：

TypeScript · 递归 Horn 子句
const reasoner = new DatalogReasoner();
reasoner.addFact({ predicate: "parent", args: ["alice", "bob"] });
reasoner.addFact({ predicate: "parent", args: ["bob", "carol"] });
reasoner.addRule("ancestor(X, Y) :- parent(X, Y).");
reasoner.addRule("ancestor(X, Z) :- parent(X, Y), ancestor(Y, Z).");
reasoner.evaluate();
reasoner.query("ancestor(alice, Z)");
// → [["alice","bob"], ["alice","carol"]]
◉

为什么 Datalog 必须自底向上？因为自顶向下（Prolog 风格）在递归规则上可能无限循环；自底向上 + 不动点保证一定终止，且能推导出所有可推导事实。

class ProvenanceManager {
  trackEntity(entity: string, source: string, meta: {...} = {}): void {
    const record: ProvenanceRecord = {
      entity, source,
      timestamp: new Date().toISOString(),
      method: meta.method ?? "unknown",
      confidence: meta.confidence,
      checksum: sha256(source + entity),   // SHA-256 完整性校验
    };
    // ...
  }

  verifyIntegrity(entity: string, source: string): boolean {
    // 重新计算 checksum，验证实体血缘完整性
    return this.records.get(entity)?.some(r => r.checksum === sha256(source + entity)) ?? false;
  }

  toProvoTurtle(): string {
    // 导出 PROV-O RDF/Turtle 供监管提交
  }
}
✓

SHA-256 checksum 的意义：它不是「锦上添花」，而是让审计轨迹防篡改——任何人篡改了来源，checksum 就对不上，完整性校验立即失败。

TypeScript · 中心性（Brandes 算法）
function betweennessCentrality(adj: Adjacency, nodes: string[]): Record<string, number> {
  const scores = Object.fromEntries(nodes.map(n => [n, 0]));
  for (const s of nodes) {
    // Brandes 算法（无权图）：单源最短路 + 依赖累加
    const stack: string[] = [];
    const sigma = new Map(nodes.map(n => [n, 0]));
    sigma.set(s, 1);
    const queue = [s];
    while (queue.length) {
      const v = queue.shift()!;
      stack.push(v);
      for (const edge of adj.out.get(v) ?? []) {
        const w = edge.target_id;
        if (dist.get(w)! < 0) { dist.set(w, dist.get(v)! + 1); queue.push(w); }
        if (dist.get(w)! === dist.get(v)! + 1) sigma.set(w, sigma.get(w)! + sigma.get(v)!);
      }
    }
    // 反向累加依赖...
  }
  return scores;
}
◉

设计决策：把图算法做成纯函数（接受 Adjacency 表示），而不是 ContextGraph 的方法，是为了可测试性与复用性——每个算法可独立单测，且避免了循环依赖。

TypeScript · 混合检索（RRF 融合）
hybridSearch(query: string, queryVector: number[], topK = 10) {
  const vectorResults  = this.search(queryVector, this.records.size);
  const keywordResults = this.keywordSearch(query, this.records.size);
  const rrf: Record<string, number> = {};
  const rank = (results, weight) => results.forEach((r, i) => {
    rrf[r.id] = (rrf[r.id] ?? 0) + weight / (60 + i + 1);   // 倒数排名融合
  });
  rank(vectorResults, 1);
  rank(keywordResults, 1);
  return Object.entries(rrf).sort((a, b) => b[1] - a[1]).slice(0, topK);
}
✓

RRF（Reciprocal Rank Fusion）把向量与关键词两个排序列表无参数地融合——比直接加权分数更稳健，因为不同检索器的分数尺度不同。
